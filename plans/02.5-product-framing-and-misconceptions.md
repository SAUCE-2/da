# Plan 02.5: Product Framing And Misconceptions

## Goal

Pause after Plan 02 to correct the product framing before adding environments, projects, and execution. This app is not mainly a metadata console. It is a customised SQL audit query store and executor: similar in spirit to a lightweight Bamboo-style runner, but tailored to storing, organising, and running SQL audit checks against Oracle databases.

## Status

- State: not started
- Depends on: Plan 02
- Blocks: Plan 03, Plan 04, Plan 05, Plan 06

## What To Clarify

- The primary product is a SQL audit query storage and execution tool.
- Audit queries are reusable SQL checks, not generic metadata records.
- Environments are selectable Oracle 19c targets such as dev, test, preprod, and prod.
- Environment options must be stored in the application database, not hard-coded.
- Projects identify which project-specific Oracle user/schema to run as on the selected environment.
- Project options must be stored in the application database, not hard-coded.
- Query execution must eventually use both selected environment and selected project.
- Plan language should avoid making the app sound like a passive metadata registry.

## Misconceptions To Fix

- Replace "metadata console" wording with "SQL audit query store and executor" or similar wording.
- Treat environment/project records as execution context, not just descriptive setup data.
- Treat project as the Oracle login/schema selection for a project, not only a team/product grouping.
- Keep the database-agnostic ambition in mind, but optimise the MVP around Oracle 19c because all current target databases are Oracle 19c.
- Avoid over-designing generic database abstraction before the Oracle execution path works.
